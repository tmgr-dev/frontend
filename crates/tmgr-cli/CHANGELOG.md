# Changelog

## Unreleased

- Local workspaces keep a hash-chained edit journal (schema 13, created by the desktop app; the CLI never migrates a workspace and keeps working on schema 12 without recording anything). Every task create or delete, title or description change and comment create, edit or delete is recorded in the same transaction with who wrote it: `human` (`cli_tty`) only when stdin and stdout are terminals and the environment has none of `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CODEX_SANDBOX*`, `TMGR_AGENT_SESSION`, `TMGR_RUN_TOKEN`, `TMGR_RUN_ID`; every other CLI write is `unattended` (`cli`). Tasks that predate the journal have no record and count as `unrecorded` until you edit them. A process that can write the workspace file directly can still forge a terminal or the file; the chain makes edits outside the app and the CLI detectable, not impossible.
- `tmgr queue` (experimental, hidden, `runner` builds): a task counts as `human` only with positive evidence in the local edit journal (created by the owner, no later non-human edit, a verified hash chain, and the text the bundle shows equal to what the owner wrote or confirmed) instead of the local activity log. `tmgr queue approve` first walks the edit journal from genesis and refuses a workspace whose journal does not verify.

## 0.8.0

- `tmgr usage [--today|--yesterday|--week|--month|--since DATE [--until DATE]] [--by tool|model|account|project|branch|day|task] [--task REF] [--tool claude|codex] [--account LABEL] [--no-scan] [--json]`: local AI tool usage (Claude Code now, Codex through the usage engine) read from the tools' own session logs by the new `tmgr-usage` crate. Without a period it shows today, 7 days and 30 days per tool and model. Every dollar figure is an API-equivalent cost at public list prices, not your subscription bill, and says so; events of models without a price are counted separately, left out of the cost and reported as a warning (`usage_unpriced`). Days follow the local time zone. A scan of new log lines runs first (`--no-scan` skips it; on a terminal a one-line note appears while the very first, large scan runs).
- Usage is linked to tasks: `--by task` and `--task REF` read the Agent work runs of your cloud workspaces (when signed in) and of all local workspaces (`--ws CODE` or `--ws local:CODE` limits it to one) and attribute each event to exactly one run, best match first: the run's session id, then branch plus time window, then repository plus time window (the repository comes from the run in `runs.json`, else from `tmgr project map`). Events that fit several runs go to an "ambiguous" bucket, listed with their candidate runs and never counted twice; the rest is "unattributed". A session that covers two tasks in a row is split by timestamp, and subagent usage follows its parent session. A workspace that cannot be read gives a warning (`usage_runs_unavailable`) and does not stop the others; signed out, cloud runs are skipped with `usage_runs_cloud_skipped`. Only `--by task` and `--task` fetch runs.
- `tmgr usage limits` (percent used, reset countdown, source and age per tool, account and window; "No limit data yet" when empty), `tmgr usage scan`, `tmgr usage accounts [list|add --tool T --root DIR --label L|remove LABEL]`, `tmgr usage pricing [show [--model TEXT]|update [--offline]]` and `tmgr usage reset` (deletes all stored usage data; needs a terminal confirmation or `--yes`). `pricing update` downloads the public LiteLLM price list over HTTPS without any credentials or usage data (size capped), saves it and re-prices stored events; `--offline` goes back to the bundled snapshot.
- `tmgr usage statusline install [--account LABEL] [--install]` prints the Claude Code `statusLine` command that reports rate limits to tmgr, the exact `settings.json` path and a diff preview, and changes nothing. With `--install` it shows the diff, asks for a confirmation in a real terminal (`--yes` never satisfies it), writes `settings.json.tmgr-backup-<timestamp>` and then the new file atomically, and prints the rollback commands. It warns when `.claude/settings*.json` in the current directory defines its own `statusLine`. `tmgr usage statusline uninstall` restores the previous command. The hidden `tmgr usage statusline-hook [--chain CMD]` reads Claude Code's JSON from stdin (at most 1 MiB), keeps a whitelisted snapshot, runs the chained previous command (2 s limit, stderr dropped) and prints only that command's output; it never fails and opens no database.
- JSON schemas `usage_summary`, `usage_limits`, `usage_accounts` and `usage_statusline`. Projects appear as `{name, hash}` only (the hash is the SHA-256 of the working directory path the tool logged); no prompt, response or tool text is ever read, stored or printed.
- `run` and `run_list` (`tmgr log --json`, `log --follow`): new nullable field `session_id`, the tool session the run was started from.
- `tmgr usage`: statusLine snapshots now reach the right account (they are filed under a hash of the account's config directory, never a path) and old snapshots are deleted after 30 days. The default `claude` and `codex` accounts are always `~/.claude` and `~/.codex`; a different `$CLAUDE_CONFIG_DIR` or `$CODEX_HOME` shows up as `claude-env` / `codex-env`. Account paths are printed as `~/...` or `<external>/name`. `usage_statusline` no longer has a `diff` field; the preview shows only the `statusLine` key, hides secret-looking commands, and an install is refused with exit 6 when `settings.json` changed while waiting. `statusline install` is refused on Windows. `pricing update --url` accepts only the LiteLLM list or a loopback address (exit 2 otherwise).
- `tmgr usage` accuracy: Claude fast mode events are priced with the LiteLLM fast multiplier, branch links need the same repository, Codex child threads follow their parent session, Codex cache writes are no longer counted as plain input, locally compacted Codex records are counted once, and a parser upgrade rewrites stored rows. Concurrent scans no longer fail. Folded days follow the local time zone. New warnings: `usage_history_dropped`, `usage_task_history_limited`, `usage_scan_bad_lines` (separate from `usage_scan_errors`) and `usage_runs_truncated`.
- Privacy: `--by task` and `--task` use your own TMGR login to read your Agent work runs (cloud and local workspaces); this is the only authenticated request. Scanning, limits and the statusLine hook need no credentials, and vendor tokens or keychains are never read.
- Experimental and hidden (`tmgr link`): `tmgr link add NAME --ssh user@host --jump JUMPLINK` reaches a follower through an existing pinned link (one hop). Both hops run with `-F none`, a dedicated key, `IdentitiesOnly`, `IdentityAgent=none`, no forwarding and `StrictHostKeyChecking=yes` against their own pinned host key; the jump is a `ProxyCommand` built from validated tokens only (absolute paths without spaces or shell characters, no `%`, no IPv6 literals). The target's host key is read through the jump at `link add` and confirmed as before; `link test` uses the jump too. The jump host's owner enrols the leader's key with `tmgr link trust KEY --as leader --name NAME --as-jump-for HOST:PORT[,...]` (privileged, at most 4 DNS-name or IPv4 destinations): the line allows forwarding to those destinations only (`permitopen`) and no remote listeners (`permitlisten` with an unmatchable host, since `none` is not accepted there), `trust` refuses unless `sshd -T` shows `AllowTcpForwarding local|yes`, `AllowStreamLocalForwarding no`, `PermitTunnel no` and `DisableForwarding no` (key options cannot block remote Unix-socket forwarding, so use a dedicated jump account with a `Match User` block), and the link answers `hello` but refuses every other method. `tmgr link list` shows it as a jump enrollment; `link revoke` removes it. Through a jump the follower sees the jump host's address, so its `link trust --from` must list that address. Every leader-to-follower connection, including `run --on`, `agents --host`, `attach --on` and `halt --on`, goes through one helper that applies the jump. A link used as a jump cannot be removed while others use it, and a jump link cannot itself be jumped.
- Cycle protection: the worker's `hello` reply gains an optional `link_key` (the follower's own link identity). `link add` now requires the follower's handshake to carry a valid `link_key` (exit 9 "too old or unidentified" otherwise; run `tmgr link init` on the follower), refuses one that has this machine's identity or already leads this machine, and stores the key; links added before this show `identity: unverified` in `link list` with a warning that cycle protection does not cover them; `link trust` refuses the key of a follower this machine leads; the worker refuses a leader whose key is its own identity or a follower of its machine. Each refusal is audited.
- Experimental and hidden, only in builds with the `runner` feature: `tmgr queue` is the local auto-run queue base (TM-521). It is off by default and starts nothing yet: the runner cannot start queue runs, so `tmgr queue run-once` records mock runs (`queue-mock-runs.json`, ids `mock-N`) and prints that no agent was started. Rules live in `~/.config/tmgr/queue.toml` (0600, directory 0700, versioned, unknown fields such as `mode` or `bypass` make the file unreadable) and only name tasks of local workspaces (`local:<code>`) assigned to a persona, with an agent profile, a repository folder, `max_concurrent` (1 to 3, 3 agents at once overall), optional `hours` (`HH-HH`, wraps midnight) and `trusted_authors` (`human` by default). A rule whose profile runs without permission prompts is refused when added and again at every pickup. `tmgr queue enable` and `tmgr queue rules add` print the risk warning and need `I AGREE` typed in a terminal; they are refused with exit 5 inside an agent session (`TMGR_RUN_TOKEN` / `TMGR_RUN_ID`), exit 10 without a terminal, and never accept `--yes`. `disable`, `pause`, `rules rm`, `rules list` and `status` need no confirmation. Each pickup is a snapshot of the run bundle (task text, comments, persona hash, launch parameters) identified by its `run_bundle.v1` sha256; `tmgr queue approve ID` shows it and needs the first 12 characters of that hash typed in a terminal; a change of the task before the start voids the approval; a task is picked once per rule until it leaves the matching state. A task counts as `human` only with positive evidence in the local activity log (created by the local owner, no later or foreign edit, comments by the owner); anything else is `unrecorded`, `agent` or `other` and is skipped and audited unless the rule lists that kind. `tmgr queue approve` shows the complete bundle (task text, every comment with its author kind, persona instructions, resolved launch line, executable and profile hashes) page by page, refuses bundles over 64 KiB, and pins the profile and executable by hash; a change before the start sends the pickup back to approval. A queue run starts in its own `git clone --reference` of the rule's repo (`<repo>-worktrees/queue/<pickup-id>`, hooks, fsmonitor and credential helpers disabled), never in your checkout, and asks the runner for `permission_mode = ask`. A run keeps its slot until it has exited, task listings are read to the last page, and a task is released only after a complete scan. Every start carries a stable key (`<pickup>-<attempt>`); a start with no recorded run id becomes `unknown_start` and keeps its slot until the runner reports the run by that key, `tmgr queue release ID` (terminal, audited) or 24 hours. An audit log that fails verification (including an unanchored entry) stops the queue until `tmgr queue enable` starts a new chain. `auto = true` is only possible for human authors and still asks for approval when a comment was written by an agent. State is `queue-state.json`, the audit is a hash-chained `queue-audit.jsonl` with an anchor file. A rules file changed outside `tmgr queue` stops the queue (exit 5) until `tmgr queue enable` confirms it.
- `tmgr usage statusline install` no longer shows `<redacted>` for its own command when tmgr is installed under a path with version digits (Homebrew Cellar, nix store, a target directory).
- Starting `gh` (PR lookup in `tmgr done`) and `git` retries briefly when the executable is momentarily busy (ETXTBSY) instead of silently skipping the PR link.

## 0.7.0

## 0.6.0

- `tmgr agent status set <session-id> --state S [--task REF] [--profile ID]`, `tmgr agent status clear <session-id>` and `tmgr agent status list [--ws CODE]`: opt-in agent status upload (metadata only: task, state, agent profile id, timestamps, the device's host label; never terminal content). `set` and `clear` need `tmgr config set upload_status true` (off by default) and the login scope `agent-status:write`; a rate-limited request exits 6 with the retry time.
- Experimental and hidden (`tmgr link`, `tmgr worker`): a leader can run agents on a follower through the follower's own runner. The worker forwards only `runs.create` with `origin {link, generation}`; the follower's runner re-checks the link scope itself under a shared lock on `~/.config/tmgr/link/links.lock`; a leader sees, attaches to and halts only its own runs; remote attach shows the follower's sanitised screen, input only with the new scope flag `allow_attach_input`. The leader commands (`tmgr run --on`, `agents --host`, `attach --on`, `halt --on`) and the runner itself are only in builds with the `runner` feature, which the release binaries do not enable yet.
- `tmgr link revoke NAME [--halt-runs]` stops that link's workers, records a tombstone (link, enrollment, generation) in `~/.config/tmgr/link/revoked.json` and, with `--halt-runs`, asks the runner to kill every run of that link; an unreachable runner, a failed revoke, unconfirmed kills or surviving runs exit 1 ("containment incomplete") and the same command retries. Link state (run ownership, worker registry, tombstones) lives in `~/.config/tmgr/link/` (0700); an old `link-runs.json` is migrated. Every worker request is audited.
- `install.sh` creates a missing install directory independently of the user's umask (it refused its own directory under umask 002); an existing group- or world-writable directory is still refused.

## 0.5.0

- Experimental and hidden from `tmgr --help`, groundwork for the runner link (no runner yet): `tmgr link` and `tmgr worker --link NAME`. Follower side: `tmgr link trust <pubkey> --as leader --name NAME [--repos DIR...] [--agents A,B] [--max N] [--from CIDR,...]` writes one `restrict,no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-user-rc,command="<abs tmgr> worker --link NAME"[,from="..."] ssh-ed25519 ... tmgr-link:NAME` line to `~/.ssh/authorized_keys` (atomic, timestamped backup, other lines untouched, a foreign line with the same key is refused, the binary must be an absolute path in a directory nobody else can write) and the scope to `~/.config/tmgr/links.toml` (0600). It checks `sshd -T` and fails closed on `PermitUserEnvironment` not `no`, a `ForceCommand`, an `AuthorizedKeysCommand`, `PermitTunnel` not `no` (unless `DisableForwarding yes`), an `AcceptEnv` beyond `LANG`, `LANGUAGE` and `LC_*`, or a missing directive; it evaluates the effective configuration for 127.0.0.1 and the first address of every `--from` CIDR, inspects every effective `AuthorizedKeysFile` for an unmanaged copy of the key, and treats `Match` blocks, glob or quoted `AuthorizedKeysFile` entries, and any `sshd_config` that cannot be read in full (`Include` is followed, bounded) as unverified ("verify manually"); if `sshd -T` cannot run it warns and needs a second typed confirmation (`unverified`). `trust` and any widening `tmgr link scope` need a terminal on stdin and stdout, are refused with exit 5 inside an agent session (`TMGR_RUN_TOKEN` / `TMGR_RUN_ID` set), need the link name typed, and never accept `--yes` (exit 10 without a terminal). `tmgr link revoke NAME` is always allowed and instant; `tmgr link list`, `tmgr link audit [--tail N] [--verify]` (SHA-256 hash chain plus a 0600 anchor file that catches tail truncation (an append that finds a mismatch writes a `chain_broken` entry and `--verify` keeps reporting it; a newest entry that is not anchored yet is reported as incomplete, never as verified), rotation at 10 MiB keeps the chain, 10 files at most and then new requests are refused, the log is 0600 in a 0700 directory; trust, scope changes and revokes run under one lock, the intent is audited before activation and failures roll the authorized_keys change back, and a failed rollback blocks the link until `tmgr link revoke NAME`; the worker also exits after 10 minutes whatever it is waiting on).
- Worker: `tmgr worker --link NAME --enrollment ID` accepts exactly that argv (the enrollment id is random per trust and baked into the forced command, so a revoke and re-trust under the same name ends old sessions; trust, scope and `from` are re-checked on every request), needs `SSH_CONNECTION` and a trusted NAME, logs `SSH_ORIGINAL_COMMAND` as length and hash only, and speaks 4-byte big-endian length plus JSON frames (at most 1 MiB, 256 requests per connection, 120 per minute, 30 s idle and 10 min per session, at most 4 concurrent workers per link) with the methods `hello`, `runs.list`, `runs.get`, `runs.create`, `runs.halt`. Run methods are checked against the leader's scope (agents, repos after canonicalisation, max, no bypass, no `on`), audited, and answered `not_available` until the runner exists. Leader side: `tmgr link init [--rotate]` (interactive; ed25519 key in the OS credential store or a 0600 file; refuses when an identity already exists in either place, `--rotate` needs the typed word `rotate`), `tmgr link add NAME --ssh user@host [--port N]` (host key pinned on first use after a typed confirmation of the fingerprint, then a `hello` handshake), `tmgr link remove NAME`, `tmgr link test NAME`. Connections run `ssh` with an isolated option set (`-F none`, own known_hosts with `HostKeyAlias`, `StrictHostKeyChecking=yes`, no agent, forwarding or multiplexing); failures exit 9. `--jump` is not supported yet. New exit code name `link` (9) in `tmgr-core`.
- A task key (`TM-537`) that is not in the default workspace is looked up in your other workspaces (at most 20) when `--ws` is not given. One match: the command runs against that workspace and prints `using workspace CODE (KEY is not in DEFAULT)` to stderr (`--json`: warning `workspace_switched`); several matches: exit 6 with the hint `add --ws CODE`; none: exit 3 as before. An explicit `--ws` never searches, and the configured default workspace is not changed.
- Argument errors use the `error:` / `hint:` format (exit 2, the JSON envelope with `--json`): `--ws` without a value, `--list` (suggests `tmgr ws list` or `tmgr task list`), and unknown subcommands or flags with clap's "did you mean" suggestion.
- `tmgr ws` alone runs `tmgr ws list`. `tmgr ws use` without a code asks for a number or code in a terminal; without one it exits 2 with the hint `tmgr ws use <code>`.
- `tmgr today` and the `TODAY` line of `tmgr status` read tracked time from the per-day endpoint `GET /api/workspaces/{id}/time/daily` (time zone from `TZ`, else the system IANA zone, else UTC with the warning `timezone_unknown`). Tracked time is now yours by default (`mine=true`: "you" in the you/agents split); previously it was workspace-wide. Status and project come from the same response, so the per-task lookups and the warnings `status_partial` and `human_time_workspace_wide` are gone. An older server without the endpoint falls back to the time summary with the warning `daily_time_unavailable`.
- `today --json`: new `tz`, and per task `url` and `users` (`id`, `name`, `human_s`). `status --json`: `today.human_s` is filled, `today.agent_s` stays null.

## 0.4.0

- `tmgr self-update [--check] [--channel stable|beta] [--allow-downgrade]`: updates the binary from a GitHub release whose `manifest.json` carries a valid minisign signature (public key compiled in; a build without a key refuses with exit 5). Checks expiry, the archive sha256 and a rollback floor kept in `~/.local/state/tmgr/update.json`; keeps `tmgr.old`; refuses Homebrew, Nix, cargo and npm installs and prints their upgrade command.
- `https://tmgr.dev/install.sh` installer, `nix/tmgr-cli.nix` (`packages.<system>.tmgr-cli`) and a Homebrew formula template; releases now include `manifest.json`.
- `tmgr today [--date YYYY-MM-DD|--yesterday] [--mine]`: tracked time per task (people), agent time per task (workspace agent work runs clipped to the day in your local time zone), status and project, a time split bar and the routines due that day. `--mine` filters agent runs by your user; tracked time of people is workspace-wide on the server and stays unfiltered (warning `human_time_workspace_wide`).
- `tmgr routine list [--date D]` and `tmgr routine done <id> [--date D]`. `done` looks the routine up first and uses the idempotent instance route, so running it twice never un-completes a routine; a routine without an instance can only be completed for today.
- `tmgr log [--task REF] [--since 2h] [--agent NAME] [--limit N] [--cursor C]`: agent work runs of the workspace, newest first. `--follow` polls every 5 seconds, prints each new or changed run once (NDJSON `{"schema":"tmgr.v1","event":"run.updated","data":{...}}` with `--json`), backs off while offline (exit 7 after about a minute) and exits 130 on Ctrl-C. A workspace with agent work turned off gives an empty result and the warning `agent_work_disabled`.
- `tmgr note [TITLE] [--title T] [--task REF] [--parent PAGE_ID]`: opens `$VISUAL` / `$EDITOR` (fallback `vi`, split into arguments without a shell) on a 0600 file in a private 0700 directory, saves the note as a page (an empty or untouched note is cancelled, exit 130) and links it to the task with a `tmgr://task/<id>` line. When saving fails the note is kept and its path is printed.
- `tmgr page pull <dir> [--tree PAGE_ID|--all] [--force]`, `tmgr page push [<file>...]`, `tmgr page status [<dir>]`: pages as `<slug>.md` files (slug `[a-z0-9-]{1,60}`, `-<id>` added on a name collision) with a `tmgr:` front matter block (`page_id`, `version`, `updated_at`, `workspace`) and a `.tmgr-pages.json` index. Files are written atomically without following symlinks and only inside `<dir>`; pull never overwrites a locally modified file without `--force`; push sends only changed files and refuses files that were not pulled. A version conflict exits 6 and writes `<slug>.remote.md` next to the file.
- JSON schemas `today`, `run_list`, `run` (the `log --follow` event), `routine_list`, `routine_done`, `page_ref`, `page_sync`, `page_status`.
- `tmgr board [-p CODE] [--mine] [--ascii]`: full-screen kanban of the workspace statuses (hidden and archived types excluded). Keys: `h/l` column, `j/k` card, `H/L` move the card to the previous/next status (optimistic, rolled back on error), `s`/`S` start/stop the timer, `c` comment, `/` filter, `Enter` details (description, last 5 comments, agent work runs), `g` refresh, `?` help, `q`/Esc quit; mouse click selects, wheel moves. Refreshes every 30 s and after each action. Below 100 columns it shows one column with a status tab strip, below 60 a plain list grouped by status. Colours follow `COLORTERM`, `NO_COLOR` and `--no-color`. Needs a terminal (exit 2 otherwise). The board always shows statuses: the Workflow module flag is not readable with a CLI token, so there is no Open/Done mode yet.
- `tmgr agent start <ref>|update|finish`: Agent work runs from the command line (`--agent`, `--model`, `--branch`; `--commit "sha subject"` repeatable, `--pr`, `--tests-passed/--tests-failed/--tests-cmd`, `--summary`, `--status`). The run id per task is kept in `~/.local/state/tmgr/runs.json` (mode 0600); `update` merges new commits with the ones already sent because the server replaces the list. A workspace with Agent work turned off gives the warning `agent_work_disabled` and exit 0.
- `tmgr hook claude <event>` and `tmgr hook codex notify`: Rust replacement of `@tmgr/notify hook ...`. The payload is read from stdin (Claude Code, at most 256 KiB) or from the last argument (Codex); the hook always exits 0, writes nothing to stdout, never refreshes or mints tokens, and is cut off after 1.5 s. `notification` pushes "needs you" (high priority), `user-prompt-submit` records the turn start, `stop` pushes "done" after turns longer than `TMGR_NOTIFY_STOP_MIN_MINUTES` (default 5). When an Agent work run is active for the branch, `stop` also sends the commits since the run start and every event heartbeats the run (at most every 5 minutes).
- `tmgr hook install|uninstall claude|codex [--project] [--print]`: shows the diff, asks (never accepts `--yes` for user-level files), writes a timestamped backup, keeps unknown keys, migrates `npx -y @tmgr/notify hook ...` entries to the absolute path of this binary. Codex has no project scope and one `notify` program, so a foreign one is refused with exit 6.
- `tmgr notify "text" [--title T] [--priority low|normal|high] [--link URL]`, `tmgr alarm "text" [--title T] [--ack-timeout 5m] [--delivery-timeout D] [--call-attempts N] [--no-call] [--no-wait] [--max-wait D]`, `tmgr alarm status [ID] [--wait SECS]`. The notify token comes from `TMGR_NOTIFY_TOKEN`, then `~/.config/tmgr-notify/env` (only when it is a private file you own), then the OS credential store (account `<server>:default:notify`), and is minted on first use with scope `notify:send`. `tmgr logout` revokes it.
- `tmgr login` drops (and tries to revoke with the old credentials) the notify token of the previous login. `agent update|finish --run ID` for a run missing from the local state needs `--task REF` and merges with the commits the server already has.
- `tmgr mcp`: stdio MCP server with `notify_user`, `alarm`, `alarm_status` and `tmgr_cli`.
- JSON schemas `agent_run`, `notify_result`, `alarm`. `serde_json` now keeps object key order, so `--json` data keys appear in insertion order.

## 0.3.0

- `tmgr start <ref>`: creates or switches to a branch from `branch_template` (default `{key_lower}-{slug}`, e.g. `tm-509-repo-prep-cargo-workspace`), moves a backlog task to the first active status, starts the timer and writes `~/.local/state/tmgr/active.json`. Flags: `--branch`, `--no-branch`, `--from`, `--no-timer`, `--status`, `--stash`. A dirty tree is refused with exit 6. A running timer on another task is stopped after confirmation (non-interactive: exit 10 unless `--yes`).
- `tmgr stop`, `tmgr switch <ref>`, `tmgr done [<ref>]` (`--status`, `--no-pr`, `--comment`, `--force`): `done` stops the timer, moves the task to the `review_status` status (default "Review", else the first completed status), looks up the PR with `gh pr view` or builds the GitHub/GitLab compare URL from `origin`, and posts it as a comment.
- `tmgr project map|unmap|list`: maps a project code to a local repository (`[projects]` in `config.toml`).
- `tmgr git install-hooks [--global]`: installs a `commit-msg` hook that chains an existing one (moved to `commit-msg.tmgr-prev`). `tmgr git hook commit-msg <file>` appends `Refs: <KEY>` for branches named after a task and never fails the commit. A global install needs an interactive confirmation.
- `tmgr prompt [--format plain|zsh|bash|fish|starship|tmux|claude]` and `tmgr statusline claude`: print `⏱ TM-509 1h12m` from the local state file only, with no network access.
- `tmgr init zsh|bash|fish|starship|tmux|claude` prints the snippet; `--install` / `--uninstall` edit the config file after showing a diff, asking, and writing a timestamped backup.
- `config` keys `branch_template` and `review_status`. Global `--yes` accepts non-privileged confirmations. New exit code 10 (needs_confirmation).
- `start` finds timers running on other tasks through `GET /api/tasks/runned` (falls back to the local state file when the route is unavailable); `tmgr status` shows the running task (the latest one, with a warning when several run).
- JSON schemas `start`, `stop`, `done`.

## 0.2.0

- `tmgr login` (`auth login`): device-code sign-in with `--scopes`, `--label`, `--no-browser`, `--with-token` (token from stdin). Tokens go to the OS credential store (macOS Keychain, Linux Secret Service) and fall back to a 0600 file when no store exists.
- `tmgr logout`, `tmgr whoami` (`auth status`), `tmgr ws list|use`, `tmgr config list|get|set|path`.
- `tmgr` / `tmgr status`: workspace and today's tracked time.
- `tmgr task show <ref>`, `tmgr task list` (cursor pagination), `tmgr add` (arguments or `-` for stdin).
- Global `--json` (schema `tmgr.v1`, JSON Schemas in `crates/tmgr-cli/schemas/tmgr.v1/`), `--ws`, `--no-color`, `-q`, `-v`, `--server`.
- Stable exit codes: 2 usage, 3 not found, 4 auth, 5 forbidden, 6 conflict, 7 offline, 130 interrupted.
- Automatic token refresh on 401 (one retry); redirects are never followed.
- Raised the minimum Rust version to 1.89.
