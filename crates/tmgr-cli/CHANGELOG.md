# Changelog

## 1.0.31

- `tmgr attach` shows the subagents a Claude Code session has running. The session row gets `(+3)` after its name, and its activity line can be clicked (or `Ctrl-] u` on the focused session) to expand one row per subagent, such as `Explore: find auth routes  0:12`. Click a subagent row to open a read-only peek of its own transcript: its prompt, what it says and the tools it calls (never their output). The peek refreshes about once a second, scrolls with Up/Down, PageUp/PageDown, `g` and `G`, and closes with `Esc`, `q` or a click; nothing you type there reaches the subagent. A subagent counts as running until its result or completion notice appears in the session transcript, and a background one that has written nothing for ten minutes is dropped. Only the last megabyte of the session transcript is read, so a subagent started before that is not shown. Codex sessions show nothing. Not in a remote attach.

## 1.0.30

- `tmgr attach` shows what each Claude Code session is doing without opening it. While a session works, a line under its name in the sidebar (and after the state in the pane header when there is room) shows the tool it is running, such as `Bash: cargo test` or `Edit: api.rs`, with the turn time `0:42`; between tools it says `thinking`; when the agent keeps a todo list (`TodoWrite`, or the `TaskCreate`/`TaskUpdate` tools) the open progress `3/7` comes first. The runner client reads the agent's own transcript (never the screen), updates about once a second and only for sessions you can see. Secret-looking values in commands (`NAME=value`, `--password x`, bearer and `Authorization:` headers, URL credentials, well-known token prefixes) are hidden. Codex sessions show nothing. Not in a remote attach.

## 1.0.29

- In the `tmgr attach` question list, `Go to` (key `g`) jumps to the place in the pane where the agent asked: the pane scrolls back to the question and its lines are highlighted, and `Esc` returns to the live screen. When the question is no longer in the scrollback (the agent uses the alternate screen, the session was resumed, or the history scrolled away) it opens `Context` instead.
- `Fork` (key `f`, Claude Code sessions only) starts a new session with the same conversation (`claude --resume <id> --fork-session`) in a split pane named `<name>-fork-N`, and pastes the question into its input once the agent is ready, like `Answer` does, without pressing Enter. The original session keeps running and its question stays open. The runner copies only the conversation file into the new session's home. Needs a restarted runner of this version (`sessions_fork.v1`). On a narrow terminal the two buttons give way to the keys.

## 1.0.28

- `tmgr attach` collects the questions your agents ask and you have not answered yet. When an agent session stops, the runner client reads the agent's own transcript (never the screen) and picks out the questions in its last message: first by rules (a sentence ending in `?` outside code and quotes, `Answer:` slots, Claude's `AskUserQuestion` tool), then Haiku through your own `claude` command (`claude -p --model haiku`, your subscription, no API key) separates real questions from rhetorical ones; when `claude` is missing, busy or over its limit the rules alone decide. A `?N` badge shows the number of open questions in the pane header, on the sidebar row and in the status line. Click it or press `Ctrl-] q` to open the list: `Context` shows your message and the agent's reply around the question, `Answer` pastes `> Earlier you asked (12 min ago): "..."` and `Answer: ` into the agent's input without pressing Enter and marks the question answered, `Ignore` hides it (the `Ignored` tab lists them and `Restore` brings one back). On a narrow terminal the buttons give way to the keys `a`, `c`, `i`, `Tab`. Questions are kept on this computer, survive a restart and never close by themselves. Detection runs while `tmgr attach` is open; each pass continues from where the last one stopped.
- New `tmgr questions` lists the open questions (`--session`, `--status open|answered|ignored|all`, `--json`), `tmgr questions answer <id>` and `tmgr questions ignore <id>` set the marks (an id prefix of 4 or more characters is enough), and `tmgr questions haiku off` stops sending agent messages to Haiku so that only the rules are used (`tmgr questions haiku on` turns it back on). With Haiku on, the text of an agent message that looks like it asks something goes through your own `claude` command, like a normal chat; it is never sent anywhere else. Not in a remote attach.

## 1.0.27

- In `tmgr attach` you can resize panes with the mouse: drag the line between two side-by-side panes, or the header row of the pane below a split (not its buttons). With nested splits the nearest split owning that line moves; both sides keep a minimum size, and the ratio is saved with the tab layout. `Ctrl-] ?` mentions it.

## 1.0.26

- `tmgr attach` has colour themes: `dark`, `light` and `high-contrast`. By default it asks the terminal for its background colour (OSC 11) at start and picks `light` or `dark`; a terminal that does not answer within a quarter of a second gets `dark`. `tmgr config set attach.theme light` (or `dark`, `high-contrast`, `auto`) overrides the detection. All sidebar, border, status and dialog colours come from the theme; the colours inside the panes are the programs' own and are not changed. Not in a remote attach.
- The `tmgr attach` sidebar is resizable: drag its right edge with the mouse, or press `Ctrl-] <` and `Ctrl-] >` (also in the command palette and `Ctrl-] ?`). The width is 16 to 60 columns, never squeezes the panes below 10 columns, and is remembered with the layout. `tmgr config set attach.sidebar_width 32` sets the default until you resize it yourself.

## 1.0.25

- `tmgr attach` has tabs, like Warp: a tab is a set of panes with its own split layout. Split right or below (`Ctrl-] |` / `Ctrl-] -`, `Ctrl-] s`) adds a pane to the current tab, and the New session dialog (`Ctrl-] c`) gets a "New tab" option next to Right, Below and Replace. The sidebar is grouped by tab: a tab with several panes shows a `▾ <name> (3)` header with its sessions under it (the folder · branch line stays under each session), a one-pane tab is a plain session row. Click a tab header or a one-pane row to switch every pane to that tab's layout; click a session inside a tab to switch to that tab and focus its pane. A session is in at most one tab. `Ctrl-] N` / `Ctrl-] P` go to the next / previous tab, `Ctrl-] ,` renames the tab (the name stays in tmgr attach, the sessions keep their names) and `Ctrl-] &` closes the tab while its sessions keep running; all of them are in `?` and the command palette. `Ctrl-] g` now switches the sidebar between grouping by tab and grouping by repo. Every tab's layout is saved and restored on the next attach; the layout saved by an older version opens as one tab. Not in a remote attach.

## 1.0.24

- `tmgr attach` counts your own time in each session and shows it in the sidebar as `you 12m`. Time counts only while the terminal window is focused, the session's pane is focused and you did something in the last 2 minutes (typing and reading are counted separately); it stops when the window loses focus, the Mac sleeps or you detach, and several attach windows on the same session never count twice. The runner stores only start and end times under its own folder, never what you type or see. Restart the runner after the update.
- New `tmgr time` shows how long you spent in `tmgr attach`, per session, folder or task (`--by`), for today (`--today`) or since a date or age (`--since 2026-10-01`, `--since 7d`), with `--json`. It reads local files only, so it works with the runner stopped. Time of sessions bound to a cloud task is sent to that task by the attach client every few minutes and when you detach, only when the workspace has session time switched on, and never twice; it is sent again later if you were offline. `tmgr time sync off` keeps all time local, `tmgr time sync` shows the state, and `tmgr time idle <seconds>` (30 to 3600) sets how long without activity before time stops counting.

## 1.0.9

- This release is still not signed (no minisign secrets), so its tarballs have SHA256SUMS only and it is published as a prerelease.
- Leak gate for mixed private/public cloud runs: before a publish pushes anything, the CLI looks up the visibility of every repository of the run (`gh repo view`). When a repository that is not known private gets commits and another repository of the run is not known public (or belongs to another owner), the commits, their messages, author and committer identities, the branch name, the pull request title and body and the changed file paths of the public side are checked against the files of the private side. It looks for copied code (token fingerprints that survive re-indenting, re-wrapping, comments, base64, hex and unicode escapes), foreign files, secrets, internal names (package prefixes, hostnames, IPs, environment variables) and content it cannot scan (binary or larger than 512 KiB files, submodules, symlinks). Single-repository runs and runs whose repositories share visibility and owner are not gated.
- A publish that the gate stops is held: nothing is pushed, no branch is left in your repositories, and the task gets one comment and the agent run is cancelled, both with categories and counts only (no repository names, paths or code). A held queue pickup frees its slot and is not published again, also not by an older CLI.
- `tmgr run <task> --review` (owner terminal only, refused in agent sessions) prints every finding with the public location, the private reference and the public diff. `--review --push` re-imports the run, refuses when a branch changed since it was held, shows the findings again and publishes after you type the repository names. `--review --drop` releases the hold after you type the task key; the run folder stays.
- `tmgr queue status` shows the status `held` with the categories.
- Known limits: the gate targets accidental and lazy copying, not a determined exfiltrator. It does not catch paraphrased code, renamed identifiers, fragments shorter than about 25 tokens, content that comes from private binary files or files over 512 KiB, or credentials outside the known patterns. The agent can still read both repositories; the environment and terminal guard on `--push` (unchanged since earlier releases) is the real barrier.

## 0.5.0

- Experimental and hidden from `tmgr --help`, groundwork for the runner link (no runner yet): `tmgr link` and `tmgr worker --link NAME`. Follower side: `tmgr link trust <pubkey> --as leader --name NAME [--repos DIR...] [--agents A,B] [--max N] [--from CIDR,...]` writes one `restrict,no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-user-rc,command="<abs tmgr> worker --link NAME"[,from="..."] ssh-ed25519 ... tmgr-link:NAME` line to `~/.ssh/authorized_keys` (atomic, timestamped backup, other lines untouched, a foreign line with the same key is refused, the binary must be an absolute path in a directory nobody else can write) and the scope to `~/.config/tmgr/links.toml` (0600). It checks `sshd -T` and fails closed on `PermitUserEnvironment` not `no`, a `ForceCommand`, an `AuthorizedKeysCommand`, `PermitTunnel` not `no` (unless `DisableForwarding yes`), an `AcceptEnv` beyond `LANG`, `LANGUAGE` and `LC_*`, or a missing directive; it evaluates the effective configuration for 127.0.0.1 and the first address of every `--from` CIDR, inspects every effective `AuthorizedKeysFile` for an unmanaged copy of the key, and treats `Match` blocks, glob or quoted `AuthorizedKeysFile` entries, and any `sshd_config` that cannot be read in full (`Include` is followed, bounded) as unverified ("verify manually"); if `sshd -T` cannot run it warns and needs a second typed confirmation (`unverified`). `trust` and any widening `tmgr link scope` need a terminal on stdin and stdout, are refused with exit 5 inside an agent session (`TMGR_RUN_TOKEN` / `TMGR_RUN_ID` set), need the link name typed, and never accept `--yes` (exit 10 without a terminal). `tmgr link revoke NAME` is always allowed and instant; `tmgr link list`, `tmgr link audit [--tail N] [--verify]` (SHA-256 hash chain plus a 0600 anchor file that catches tail truncation (an append that finds a mismatch writes a `chain_broken` entry and `--verify` keeps reporting it; a newest entry that is not anchored yet is reported as incomplete, never as verified), rotation at 10 MiB keeps the chain, 10 files at most and then new requests are refused, the log is 0600 in a 0700 directory; trust, scope changes and revokes run under one lock, the intent is audited before activation and failures roll the authorized_keys change back, and a failed rollback blocks the link until `tmgr link revoke NAME`; the worker also exits after 10 minutes whatever it is waiting on).
- Worker: `tmgr worker --link NAME --enrollment ID` accepts exactly that argv (the enrollment id is random per trust and baked into the forced command, so a revoke and re-trust under the same name ends old sessions; trust, scope and `from` are re-checked on every request), needs `SSH_CONNECTION` and a trusted NAME, logs `SSH_ORIGINAL_COMMAND` as length and hash only, and speaks 4-byte big-endian length plus JSON frames (at most 1 MiB, 256 requests per connection, 120 per minute, 30 s idle and 10 min per session, at most 4 concurrent workers per link) with the methods `hello`, `runs.list`, `runs.get`, `runs.create`, `runs.halt`. Run methods are checked against the leader's scope (agents, repos after canonicalisation, max, no bypass, no `on`), audited, and answered `not_available` until the runner exists. Leader side: `tmgr link init [--rotate]` (interactive; ed25519 key in the OS credential store or a 0600 file; refuses when an identity already exists in either place, `--rotate` needs the typed word `rotate`), `tmgr link add NAME --ssh user@host [--port N]` (host key pinned on first use after a typed confirmation of the fingerprint, then a `hello` handshake), `tmgr link remove NAME`, `tmgr link test NAME`. Connections run `ssh` with an isolated option set (`-F none`, own known_hosts with `HostKeyAlias`, `StrictHostKeyChecking=yes`, no agent, forwarding or multiplexing); failures exit 9. `--jump` is not supported yet. New exit code name `link` (9) in `tmgr-core`.
- A task key (`TM-537`) that is not in the default workspace is looked up in your other workspaces (at most 20) when `--ws` is not given. One match: the command runs against that workspace and prints `using workspace CODE (KEY is not in DEFAULT)` to stderr (`--json`: warning `workspace_switched`); several matches: exit 6 with the hint `add --ws CODE`; none: exit 3 as before. An explicit `--ws` never searches, and the configured default workspace is not changed.
- Argument errors use the `error:` / `hint:` format (exit 2, the JSON envelope with `--json`): `--ws` without a value, `--list` (suggests `tmgr ws list` or `tmgr task list`), and unknown subcommands or flags with clap's "did you mean" suggestion.
- `tmgr ws` alone runs `tmgr ws list`. `tmgr ws use` without a code asks for a number or code in a terminal; without one it exits 2 with the hint `tmgr ws use <code>`.
- `tmgr today` and the `TODAY` line of `tmgr status` read tracked time from the per-day endpoint `GET /api/workspaces/{id}/time/daily` (time zone from `TZ`, else the system IANA zone, else UTC with the warning `timezone_unknown`). Tracked time is now yours by default (`mine=true`: "you" in the you/agents split); previously it was workspace-wide. Status and project come from the same response, so the per-task lookups and the warnings `status_partial` and `human_time_workspace_wide` are gone. An older server without the endpoint falls back to the time summary with the warning `daily_time_unavailable`.
- `today --json`: new `tz`, and per task `url` and `users` (`id`, `name`, `human_s`). `status --json`: `today.human_s` is filled, `today.agent_s` stays null.

## 0.4.0

- `tmgr self-update [--check] [--channel stable|beta] [--allow-downgrade]`: updates the binary from a GitHub release whose `manifest.json` carries a valid minisign signature (public key compiled in; a build without a key refuses with exit 5). Checks expiry, the archive sha256 and a rollback floor kept in `~/.local/state/tmgr/update.json`; keeps `tmgr.old`; refuses Homebrew, Nix, cargo and npm installs and prints their upgrade command.
- `https://tmgr.dev/install.sh` installer, `nix/tmgr-cli.nix` (`packages.<system>.tmgr-cli`) and a Homebrew formula template; releases now include `manifest.json`.
- `tmgr today [--date YYYY-MM-DD|--yesterday] [--mine]`: tracked time per task (people), agent time per task (workspace agent work runs clipped to the day in your local time zone), status and project, a time split bar and the routines due that day. `--mine` filters agent runs by your user; tracked time of people is workspace-wide on the server and stays unfiltered (warning `human_time_workspace_wide`).
- `tmgr routine list [--date D]` and `tmgr routine done <id> [--date D]`. `done` looks the routine up first and uses the idempotent instance route, so running it twice never un-completes a routine; a routine without an instance can only be completed for today.
- `tmgr log [--task REF] [--since 2h] [--agent NAME] [--limit N] [--cursor C]`: agent work runs of the workspace, newest first. `--follow` polls every 5 seconds, prints each new or changed run once (NDJSON `{"schema":"tmgr.v1","event":"run.updated","data":{...}}` with `--json`), backs off while offline (exit 7 after about a minute) and exits 130 on Ctrl-C. A workspace with agent work turned off gives an empty result and the warning `agent_work_disabled`.
- `tmgr note [TITLE] [--title T] [--task REF] [--parent PAGE_ID]`: opens `$VISUAL` / `$EDITOR` (fallback `vi`, split into arguments without a shell) on a 0600 file in a private 0700 directory, saves the note as a page (an empty or untouched note is cancelled, exit 130) and links it to the task with a `tmgr://task/<id>` line. When saving fails the note is kept and its path is printed.
- `tmgr page pull <dir> [--tree PAGE_ID|--all] [--force]`, `tmgr page push [<file>...]`, `tmgr page status [<dir>]`: pages as `<slug>.md` files (slug `[a-z0-9-]{1,60}`, `-<id>` added on a name collision) with a `tmgr:` front matter block (`page_id`, `version`, `updated_at`, `workspace`) and a `.tmgr-pages.json` index. Files are written atomically without following symlinks and only inside `<dir>`; pull never overwrites a locally modified file without `--force`; push sends only changed files and refuses files that were not pulled. A version conflict exits 6 and writes `<slug>.remote.md` next to the file.
- JSON schemas `today`, `run_list`, `run` (the `log --follow` event), `routine_list`, `routine_done`, `page_ref`, `page_sync`, `page_status`.
- `tmgr board [-p CODE] [--mine] [--ascii]`: full-screen kanban of the workspace statuses (hidden and archived types excluded). Keys: `h/l` column, `j/k` card, `H/L` move the card to the previous/next status (optimistic, rolled back on error), `s`/`S` start/stop the timer, `c` comment, `/` filter, `Enter` details (description, last 5 comments, agent work runs), `g` refresh, `?` help, `q`/Esc quit; mouse click selects, wheel moves. Refreshes every 30 s and after each action. Below 100 columns it shows one column with a status tab strip, below 60 a plain list grouped by status. Colours follow `COLORTERM`, `NO_COLOR` and `--no-color`. Needs a terminal (exit 2 otherwise). The board always shows statuses: the Workflow module flag is not readable with a CLI token, so there is no Open/Done mode yet.
- `tmgr agent start <ref>|update|finish`: Agent work runs from the command line (`--agent`, `--model`, `--branch`; `--commit "sha subject"` repeatable, `--pr`, `--tests-passed/--tests-failed/--tests-cmd`, `--summary`, `--status`). The run id per task is kept in `~/.local/state/tmgr/runs.json` (mode 0600); `update` merges new commits with the ones already sent because the server replaces the list. A workspace with Agent work turned off gives the warning `agent_work_disabled` and exit 0.
- `tmgr hook claude <event>` and `tmgr hook codex notify`: Rust replacement of `@tmgr/notify hook ...`. The payload is read from stdin (Claude Code, at most 256 KiB) or from the last argument (Codex); the hook always exits 0, writes nothing to stdout, never refreshes or mints tokens, and is cut off after 1.5 s. `notification` pushes "needs you" (high priority), `user-prompt-submit` records the turn start, `stop` pushes "done" after turns longer than `TMGR_NOTIFY_STOP_MIN_MINUTES` (default 5). When an Agent work run is active for the branch, `stop` also sends the commits since the run start and every event heartbeats the run (at most every 5 minutes).
- `tmgr hook install|uninstall claude|codex [--project] [--print]`: shows the diff, asks (never accepts `--yes` for user-level files), writes a timestamped backup, keeps unknown keys, migrates `npx -y @tmgr/notify hook ...` entries to the absolute path of this binary. Codex has no project scope and one `notify` program, so a foreign one is refused with exit 6.
- `tmgr notify "text" [--title T] [--priority low|normal|high] [--link URL]`, `tmgr alarm "text" [--title T] [--ack-timeout 5m] [--delivery-timeout D] [--call-attempts N] [--no-call] [--no-wait] [--max-wait D]`, `tmgr alarm status [ID] [--wait SECS]`. The notify token comes from `TMGR_NOTIFY_TOKEN`, then `~/.config/tmgr-notify/env` (only when it is a private file you own), then the OS credential store (account `<server>:default:notify`), and is minted on first use with scope `notify:send`. `tmgr logout` revokes it.
- `tmgr login` drops (and tries to revoke with the old credentials) the notify token of the previous login. `agent update|finish --run ID` for a run missing from the local state needs `--task REF` and merges with the commits the server already has.
- `tmgr mcp`: stdio MCP server with `notify_user`, `alarm`, `alarm_status` and `tmgr_cli`.
- JSON schemas `agent_run`, `notify_result`, `alarm`. `serde_json` now keeps object key order, so `--json` data keys appear in insertion order.

## 0.3.0

- `tmgr start <ref>`: creates or switches to a branch from `branch_template` (default `{key_lower}-{slug}`, e.g. `tm-509-repo-prep-cargo-workspace`), moves a backlog task to the first active status, starts the timer and writes `~/.local/state/tmgr/active.json`. Flags: `--branch`, `--no-branch`, `--from`, `--no-timer`, `--status`, `--stash`. A dirty tree is refused with exit 6. - `tmgr git install-hooks [--global]`: installs a `commit-msg` hook that chains an existing one (moved to `commit-msg.tmgr-prev`). `tmgr git hook commit-msg <file>` appends `Refs: <KEY>` for branches named after a task and never fails the commit. A global install needs an interactive confirmation.
- `tmgr prompt [--format plain|zsh|bash|fish|starship|tmux|claude]` and `tmgr statusline claude`: print `⏱ TM-509 1h12m` from the local state file only, with no network access.
- `tmgr init zsh|bash|fish|starship|tmux|claude` prints the snippet; `--install` / `--uninstall` edit the config file after showing a diff, asking, and writing a timestamped backup.
- `config` keys `branch_template` and `review_status`. Global `--yes` accepts non-privileged confirmations. New exit code 10 (needs_confirmation).
- `start` finds timers running on other tasks through `GET /api/tasks/runned` (falls back to the local state file when the route is unavailable); `tmgr status` shows the running task (the latest one, with a warning when several run).
- JSON schemas `start`, `stop`, `done`.
